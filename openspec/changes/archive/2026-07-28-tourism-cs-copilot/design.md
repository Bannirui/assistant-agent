## Context

旅游企业客服团队使用现有工单系统处理客诉，客服需要在多个系统间切换查询信息，效率低下。本项目构建一个 AI Copilot，以工单号为唯一入口，自动聚合分析上下文，给出回复建议。系统采用全真模拟——所有外部系统（OMS/PMS/CRM/Policy/工单系统）均以接口 Mock 方式搭建。操作深度为浅层（只给建议，客服确认后自行操作）。

## Goals / Non-Goals

**Goals:**
- 构建 ReAct Agent 架构，LLM 自主决策调用工具链
- Agent 只暴露通用 Tool 接口，内部 Router 按 product_category 分发到对应 Mock 系统
- 退改金额等确定性计算走计算引擎，LLM 不参与数值计算
- SOP 引擎提供结构化决策表+话术模板，覆盖常见客诉场景
- RAG 知识库作为 SOP 未覆盖场景的兜底检索
- 前端提供结构化工作台（左侧对话 + 右侧 Copilot 分析面板）

**Non-Goals:**
- 不实现实际的外部系统对接（全部 Mock）
- 不实现 Agent 自动执行操作（退款/改签等），仅输出建议
- 不实现多租户/权限体系
- 不实现工单系统的写入能力（只读）
- 不实现从文档自动生成 SOP 的能力（SOP 为人工编写）

## Decisions

### D1: Agent 架构 — 混合模式（原生 Function Calling + LangChain Tools + 状态机）

**选择**: Agent 不同层次采用不同实现方式，各司其职：

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  ① 原生 Function Calling（Agent 决策层）                  │
│     ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━                    │
│     ReAct 大循环：LLM 决定调哪个工具、调几次、何时停       │
│     自己拼 messages、解析 function_call、执行循环        │
│     不引入框架的黑盒抽象                                   │
│                                                         │
│  ③ LangChain @tool（工具定义层）                          │
│     ━━━━━━━━━━━━━━━━━━━━━━                               │
│     用 @tool 装饰器包装每个工具函数                       │
│     自动生成 OpenAI 格式的 function schema               │
│     避免手写 JSON Schema 出错                             │
│                                                         │
│  ② 状态机（确定性子流程）                                  │
│     ━━━━━━━━━━━━━━━━━━                                   │
│     计算引擎和 SOP 引擎内部使用状态机建模                  │
│     如 calculate_refund：                                │
│     [获取订单] → [查舱位规则] → [叠加VIP] → [返回结果]    │
│     确定性逻辑，每步可追踪、可审计                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**理由**:
- 决策层裸写：ReAct 循环核心就一个 while 循环，框架反而增加黑盒
- 工具层用框架：`@tool` 的 schema 自动生成比手写更可靠，体现知道框架边界
- 计算层用状态机：涉及金额的确定性操作，LLM 不应参与决策，状态机保证可审计

**替代方案**:
- 纯 LangChain Agent：全链路用框架，但抽象层过多，不利于理解底层机制和面试展示
- 完全不用框架：工具 Schema 手写易出错，且面试时缺乏框架经验无法展开讲

### D2: 工具层设计 — 通用接口 + 内部路由

**选择**: Agent 看到的工具是通用接口（如 `get_order(order_id)`），内部 Router 根据工单的 `category` 字段分发到对应的 Mock 系统。

```
Agent 视角:                         内部路由:
                                    
get_order(order_id)                 category="机票" → FlightOMS.get_order()
get_customer(customer_id)           category="酒店" → HotelOMS.get_order()
get_policy(category, issue)         category="火车" → TrainOMS.get_order()
search_knowledge(query)             category="打车" → RideOMS.get_order()
search_sop(category, issue_type)
calculate_refund(order, user)
```

**理由**: Agent 不需要感知品类与系统的映射关系。新增"游轮"品类时，只需在 Router 层注册新映射，Agent 零改动。

**替代方案**: 为每个品类暴露独立工具（`get_flight_order`, `get_hotel_order` 等）——Agent 工具列表随品类膨胀，System Prompt 越来越长，不符合"工具少而精"的原则。

### D3: 三引擎架构

**选择**: 核心分析能力拆分为三个独立引擎：

```
┌─────────────────────────────────────────────────────────────┐
│                        Agent (LLM)                          │
│                                                             │
│   工具层                                                      │
│   ├── get_ticket()          → 工单系统 Mock API              │
│   ├── get_order()           → 订单 Router + 下游 Mock        │
│   ├── get_customer()        → CRM Mock API                   │
│   ├── search_policy()       → 规则库 Mock API                │
│   ├── search_sop()          → SOP 引擎                       │
│   ├── calculate_refund()    → 计算引擎                       │
│   └── search_knowledge()    → RAG 知识库                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘

三个引擎的职责边界：

SOP 引擎:   结构化决策 + 话术模板。输入 category + issue_type，输出 SOP 文档
计算引擎:   确定性数值计算。输入订单+用户结构化数据，输出精确金额
RAG 知识库: 语义检索。输入查询文本，输出相关文档片段
```

**理由**:
- SOP 引擎和计算引擎边界明确：前者处理"流程和话术"，后者处理"金额和数值"
- RAG 作为兜底：SOP 覆盖不到的客诉，通过检索公司文档让 Agent 自行理解
- 三者解耦可独立迭代：运营维护 SOP 不碰计算逻辑，改计算逻辑不影响 RAG

### D4: 技术栈选型

| 组件 | 选择 | 理由 |
|------|------|------|
| 后端框架 | FastAPI (Python) | 异步原生，Type Hints 自动生成 API 文档，生态活跃 |
| Agent 决策层 | 原生 Function Calling | 裸写 ReAct 循环，理解底层机制，不引入框架黑盒 |
| Agent 工具层 | LangChain @tool | 自动生成 OpenAI 格式 function schema，避免手写出错 |
| 确定性子流程 | 状态机 | 计算引擎和 SOP 执行的可追踪、可审计 |
| 前端框架 | Vue 3 | 生态成熟，Pinia 状态管理原生支持 |
| UI 组件库 | Element Plus | 企业后台场景组件最全，表格/表单/卡片/弹窗开箱即用 |
| 状态管理 | Pinia | Vue 3 官方推荐，组合式 API 风格 |
| 打包工具 | Vite | 开发体验好，HMR 快 |
| 业务数据库 | SQLite | 零配置，单文件，本地模拟企业数据 |
| 向量数据库 | Qdrant (本地模式) | 零配置，Python 原生，数据存本地文件，跟 SQLite 同样轻量 |
| SOP 存储 | YAML | 人可读写，Git diff 友好，运营人员可编辑 |
| Mock 系统 | FastAPI 同进程 | 统一框架，降低运维复杂度 |
| 容器化 | Docker Compose | 本地全量启动，模拟企业多服务环境 |

### D7: LLM/Embedding Provider 抽象

**选择**: 定义一个 `LLMProvider` 抽象接口，统一 `chat()` 和 `embed()` 两个方法。所有供应商通过配置切换，不改代码。

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   Agent 代码（不关心底层是 DeepSeek 还是 OpenAI）       │
│                    │                                 │
│                    ▼                                 │
│   ┌──────────────────────────────────────────────┐  │
│   │           LLMProvider 接口                    │  │
│   │                                              │  │
│   │   chat(messages, tools) → response           │  │
│   │   embed(texts) → vectors                     │  │
│   └───────┬──────────┬──────────┬────────────────┘  │
│           │          │          │                    │
│           ▼          ▼          ▼                    │
│   ┌───────────┐┌───────────┐┌───────────┐           │
│   │ DeepSeek  ││  OpenAI   ││  通义千问  │           │
│   │ Adapter   ││  Adapter  ││  Adapter   │           │
│   └───────────┘└───────────┘└───────────┘           │
│                                                      │
│   配置 (config.yaml):                                 │
│   ──────────────────                                  │
│   llm:                                               │
│     provider: deepseek    # 换 openai / qwen          │
│     model: deepseek-chat                              │
│     api_key: ${DEEPSEEK_API_KEY}                      │
│     base_url: https://api.deepseek.com/v1            │
│                                                      │
│   embedding:                                          │
│     provider: dashscope  # 换 openai / local          │
│     model: text-embedding-v3                          │
│     api_key: ${DASHSCOPE_API_KEY}                     │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**理由**:
- DeepSeek 和通义千问都兼容 OpenAI SDK 接口格式，只需配 base_url + api_key + model 即可切换
- 不引入 LangChain 的 Model 抽象——场景只需要 chat 和 embed 两个接口，自建抽象更轻量
- 新增供应商只需实现 `LLMProvider` 接口，注册到配置即可
- 面试叙事："供应商无关的 LLM 抽象层，配置切换不碰业务代码"

**默认配置**: LLM 使用 DeepSeek（国产 Function Calling 最强），Embedding 使用通义千问/BGE（MTEB 榜单领先）

**替代方案**: 直接用 OpenAI SDK 硬编码单一供应商——简单但失去灵活性，不符合企业级工程标准

### D5: 操作建议的生成方式

**选择**: Agent 输出意图和上下文，操作建议由 SOP 引擎/计算引擎结构化返回，前端渲染为可点击按钮。Agent 不直接生成"建议执行退款 ¥234"这样的文本。

```
Agent 输出:                        前端渲染:

{                                   [建议操作]
  "analysis": "用户投诉...",        ┌──────────────────┐
  "reply_template": "...",         │ [发起退款 ¥234]   │
  "suggested_actions": [           │ [升级主管]         │
    {                              │ [发放补偿券]       │
      "type": "refund",            └──────────────────┘
      "label": "发起退款 ¥234",
      "amount": 234               ← 来自计算引擎，非 LLM 生成
    },
    {
      "type": "escalate",
      "label": "升级主管"
    }
  ]
}
```

**理由**: 操作建议的具体参数（尤其是金额）必须来自确定性系统，防止 LLM 幻觉导致错误操作建议。

## Risks / Trade-offs

- **[R1] Agent 幻觉风险**: LLM 可能在回复建议中编造不存在的政策或金额 → 缓解：金额走计算引擎，政策走 SOP 引擎或 RAG；操作建议由引擎输出而非 LLM 生成
- **[R2] Agent 调用次数不可控**: ReAct Agent 可能在复杂工单中调用过多轮工具 → 缓解：设置 max_iterations 上限；System Prompt 约束"不确定时宁可说不知道，不要反复查"
- **[R3] SOP 覆盖不足**: 新品类或冷门客诉无对应 SOP → 缓解：RAG 知识库兜底；SOP 引擎返回"无匹配"时 Agent 自动走 RAG 路径
- **[R4] Mock 系统维护成本**: 多个 Mock 系统接口需要维护 → 缓解：统一使用 FastAPI 同进程 Mock，共享接口定义，减少独立服务数
- **[R5] 前端复杂度**: 双面板实时联动 → 缓解：先出 MVP（一次分析、静态展示），再迭代实时交互
